# TracePixels 專案憲章

## 核心原則

### I. 原生 macOS，純 Swift

應用程式 MUST 為以 Swift 撰寫、由 Xcode 專案建置的原生 macOS 應用程式。
MUST NOT 使用跨平台執行環境、以 Web View 作為主要 UI，或為核心功能嵌入非 Swift 引擎。
系統能力（截圖、剪貼簿、拖放、分享、外觀、快速鍵）MUST 使用平台原生框架，
讓應用程式的行為符合 Mac 使用習慣。

理由：本專案的目的就是做出原生 macOS 的截圖與標註工具；原生的行為與效能是重點。

### II. 隱私與本機優先

截圖、標註與偏好設定 MUST 留在使用者的電腦上。除非使用者明確執行分享或匯出，
應用程式 MUST NOT 透過網路傳送影像資料或使用資料。螢幕錄製權限 MUST 僅在需要時才請求；
權限未授予時，應用程式 MUST 清楚說明缺少什麼，而不是產出空白影像。

理由：螢幕截圖常含有敏感資訊。

### III. 非破壞性編輯，不可還原的遮蔽

標註 MUST 以獨立物件的形式儲存在原始截圖之上，使每一個標註在匯出前都能被選取、編輯與刪除。
編輯行為 MUST NOT 修改原始截圖的像素。模糊與馬賽克在匯出檔案中 MUST 不可還原：
不得從匯出的影像中復原被遮蔽區域的原始內容。

理由：可編輯性讓工具好用，不可還原的遮蔽讓工具安全。

### IV. 核心邏輯測試先行

不需要螢幕或視窗伺服器的邏輯（標註模型、幾何與點擊測試、復原／重做、持久化、
合成與匯出、遮蔽）MUST 有自動化測試，且 MUST 在實作之前或與實作同時撰寫。
遮蔽的不可還原性 MUST 由自動化測試涵蓋。無法自動化的 UI 與截圖行為 MUST 有文件化的手動測試程序。

理由：標註與匯出流程是最容易出現無聲錯誤、且最傷害使用者的地方，同時也是最容易測試的部分。

### V. 簡單與範圍紀律

功能 MUST 能追溯到已核准的規格。目前規格中列為範圍外的項目（錄影、GIF、捲動或全景截圖、OCR、
雲端同步）在未先修訂規格前 MUST NOT 加入。新增相依套件 MUST 在計畫中說明理由，
且優先採用 Apple 框架而非第三方套件。新增的複雜度 MUST 連同理由一併記錄。

理由：一個小而完成的截圖標註工具，勝過一個龐大但未完成的工具。

### VI. 繁體中文溝通與文件

與使用者的所有對話 MUST 使用繁體中文（zh-TW）。所有由 Claude 產生的文件，包括但不限於
規格（spec）、計畫（plan）、任務（tasks）、檢查清單、研究與資料模型文件、`CLAUDE.md`、
PR 標題與描述、commit 訊息，MUST 以繁體中文撰寫。以下內容可保留原文：程式碼、識別名稱、
檔案路徑、指令、Spec Kit 與 Apple 框架的專有名詞，以及模板規定的固定標記
（例如 `[NEEDS CLARIFICATION]`、`FR-001`、`Given／When／Then` 的關鍵結構）。

理由：使用者以繁體中文閱讀與審查，文件語言一致可降低審查成本。

### VII. 自主執行 SDD 流程，以 PR 交付

Spec-Driven Development 流程（specify → clarify → plan → tasks → analyze → implement）
MUST 由 Claude 自主從頭執行到完成，MUST NOT 在過程中向使用者詢問問題或要求確認。規則如下：

- **澄清迴圈**：執行 `/speckit-clarify` 時，MUST 採用 Claude 自己的所有建議答案並寫回規格，
  然後 MUST 重複澄清，直到不再有任何需要澄清的事項為止。若同一項目連續三輪仍重複出現，
  MUST 將其記錄為「假設」並繼續，避免無窮迴圈。
- **其他步驟**：遇到模糊之處，MUST 依據專案脈絡與業界慣例自行做出最佳決策，
  並將決策與理由記錄在規格的「假設」或計畫的對應段落中，而不是提問。
- **持續推進**：MUST 依序完成所有後續步驟（plan、tasks、analyze、implement、converge），
  直到全部任務完成且建置與測試通過。
- **交付**：流程完成後 MUST 建立 Pull Request 供使用者審查。工作 MUST 在功能分支上進行，
  MUST NOT 直接推送到主要分支，也 MUST NOT 自行合併 PR。PR 是使用者唯一的審查關卡。
- **例外**：只有在遇到無法自行排除的技術阻礙時（例如沒有可用的遠端儲存庫、缺少必要的系統權限
  而無法繼續），才可停止並向使用者回報；回報 MUST 說明已嘗試的做法與卡住的原因。
  此自主授權不得凌駕其他原則（I–VI），也不涵蓋刪除既有工作、強制推送，或 PR 之外的對外發布。

理由：使用者希望把審查集中在最終成果上，而不是流程中的每一步。

## 平台與技術限制

- 語言與專案：Swift，使用 Xcode 專案。Swift Package Manager MAY 用於模組化或相依管理。
- 截圖 MUST 以顯示器的原生像素解析度擷取，包含 Retina 與混合縮放比例的多螢幕環境。
- UI MUST 支援淺色與深色外觀。
- 最低支援的 macOS 版本與 UI 框架（AppKit、SwiftUI 或混合）由實作計畫決定；
  一旦決定，MUST 記錄在計畫中，並在整個程式碼庫中保持一致。
- 目前範圍的匯出格式為 PNG 與 JPEG。

## 開發流程與品質關卡

- 工作遵循 Spec Kit 流程：specify、clarify、plan、tasks、analyze、implement，規格存放於 `specs/`，
  並依原則 VII 自主執行。
- 每項變更合併前 MUST 能在 Xcode 乾淨建置並通過自動化測試。
- 每份計畫 MUST 包含針對原則 I–VII 的憲章檢查（Constitution Check），
  違反之處 MUST 連同理由列在計畫的複雜度追蹤中。
- Xcode 專案建立後，`CLAUDE.md` MUST 更新建置、測試與單一測試的指令，以及高階架構。

本憲章優先於其他專案慣例。修訂 MUST 透過編輯本檔案進行，並附上文件化的理由、版本號異動，
以及更新「最後修訂」日期，同時 MUST 包含相依規格與計畫所需的調整。

版本號採語意化版本：移除或以不向後相容的方式重新定義原則為 MAJOR；新增原則或實質擴充指引為 MINOR；
